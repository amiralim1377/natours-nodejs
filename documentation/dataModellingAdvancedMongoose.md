## فصل اول: مدلسازی داده‌ها و معماری پیشرفته در MongoDB

مدلسازی داده (`Data Modeling`) احتمالاً مهم‌ترین و پیچیده‌ترین تصمیمی است که یک توسعه‌دهنده بک‌اند می‌گیرد. در این مرحله، ما کوهی از داده‌های بدون ساختار (`Unstructured Data`) در دنیای واقعی را می‌گیریم و آن‌ها را به یک مدل منطقی تبدیل می‌کنیم.

> **نکته طلایی:** در مدلسازی داده، هیچ «جواب کاملاً درست» یا «کاملاً غلطی» وجود ندارد. همه‌چیز به این بستگی دارد که اپلیکیشن شما قرار است چه سوالاتی از دیتابیس بپرسد (`Use cases`).

### 1. انواع ارتباطات داده‌ای (Data Relationships)

در دیتابیس‌های رابطه‌ای (`SQL`)، روابط بین جداول می‌توانند شامل **یک‌به‌یک (One-to-One)**، **یک‌به‌چند (One-to-Many)** و **چندبه‌چند (Many-to-Many)** باشند.

اما در MongoDB، به دلیل ماهیت **Document-Based** و محدودیت‌هایی مانند حداکثر اندازه‌ی یک Document، طراحی ارتباطات معمولاً بر اساس تعداد داده‌های مرتبط و نحوه‌ی دسترسی به داده‌ها به دسته‌های دقیق‌تری تقسیم می‌شود:

- **1. ارتباط یک‌به‌یک (`One-to-One`):**
- _مثال:_ یک کاربر و تنظیمات پروفایل او (مانند انتخاب تم دارک یا لایت).

- **2. ارتباط یک‌به‌تعداد کم (`One-to-Few`):**
- _مثال واقعی:_ یک دستور پخت غذا و مواد لازم آن (مواد لازم نهایتاً 10 تا 20 قلم هستند).

- **3. ارتباط یک‌به‌زیاد (`One-to-Many`):**
- _مثال واقعی:_ یک پست اینستاگرام و کامنت‌های آن (ممکن است هزاران کامنت داشته باشد).

- **4. ارتباط یک‌به‌بی‌نهایت (`One-to-Ton` / `Millions`):**
- _مثال واقعی:_ سنسور دمای یک گلخانه که هر ثانیه یک رکورد ثبت می‌کند، یا لاگ‌های خطای یک سرور.

- **5. ارتباط چندبه‌چند (`Many-to-Many`):**
- _مثال واقعی:_ محصولات و دسته‌بندی‌ها در یک فروشگاه (یک موبایل هم در دسته «کالای دیجیتال» است هم «موبایل»؛ و دسته «موبایل» هم هزاران گوشی دارد).

### 3. فریم‌ورک تصمیم‌گیری (چه زمانی کدام روش را انتخاب کنیم؟)

برای انتخاب بین `Embed` و `Reference`، هرگز فقط به یک عامل تکیه نکنید. همیشه این 3 معیار را با هم بسنجید:

-**معیار اول: نوع ارتباط (`Relationship Type`)**

-**معیار دوم: الگوی دسترسی (`Read/Write Ratio`)**

-**معیار سوم: استقلال داده (`Data Closeness`)**

---

**معیار اول: نوع ارتباط (`Relationship Type`)**
---

### 1.1 ارتباط `One-to-Few` ⬅️ معمولاً `Embed`

زمانی که یک Document تعداد کمی داده مرتبط دارد و این داده‌ها همیشه همراه آن خوانده می‌شوند، بهتر است آن‌ها را داخل همان Document ذخیره کنیم.

**مثال: یک کاربر و شماره تلفن‌های او**

یک کاربر معمولاً تعداد محدودی شماره تلفن دارد:

```javascript
{
  _id: 1,
  name: "Ali",
  phones: [
    "09121234567",
    "09351234567"
  ]
}
```

### 1.2 ارتباطات `One-to-Ton` و `Many-to-Many` ⬅️ معمولاً `Reference`

## مثال One-to-Ton (یک به خیلی زیاد)

زمانی که یک Document می‌تواند هزاران یا میلیون‌ها Document مرتبط داشته باشد، نباید آن‌ها را داخل یک Array بزرگ ذخیره کنیم.

### مثال: سنسور دما و رکوردهای اندازه‌گیری

فرض کنید یک سنسور در هر ثانیه دما را ذخیره می‌کند.
❌ روش اشتباه (Embedding):

```javascript
{
  _id: 1,
  name: "Greenhouse Sensor",
  measurements: [
    {
      temperature: 25,
      date: "2026-07-26T10:00"
    },
    {
      temperature: 26,
      date: "2026-07-26T10:01"
    }

    // میلیون‌ها رکورد دیگر...
  ]
}
```

---

**معیار دوم: الگوی دسترسی (`Read/Write Ratio`)**

- **بیشتر خوانده می‌شود، کمتر آپدیت می‌شود:** (مثال: تصاویر گالریِ یک محصول). این داده‌ها را **`Embed`** کنید تا با یک بار لود شدن محصول، عکس‌ها نیز لود شوند.
- **مدام در حال آپدیت است:** (مثال: تعداد لایک‌ها). این موارد را **`Reference`** بدهید؛ زیرا آپدیت کردنِ مداومِ یک فیلد در داخلِ یک داکیومنتِ تودرتو (`Nested`)، فشار زیادی به دیتابیس وارد می‌کند.

---

**معیار سوم: استقلال داده (`Data Closeness`)**

گاهی دو موجودیت به هم مرتبط هستند، اما یکی از آن‌ها نیاز دارد به صورت مستقل جستجو یا مدیریت شود. در این حالت بهتر است از `Reference` استفاده کنیم.

**مثال: محصولات و تصاویر (`Products & Images`)**

از نظر منطقی تصویر متعلق به محصول است:

```

Product
|
└── Images

```

### حالت اول: `Embedding`

```javascript
{
  name: "iPhone 15",
  images: [
    "front.jpg",
    "back.jpg"
  ]
}
```

مناسب است زمانی که:

- تصاویر فقط همراه محصول استفاده می‌شوند.
- تعداد تصاویر محدود است.

---

### حالت دوم: `Reference`

اگر تصاویر نیاز به جستجوی مستقل داشته باشند (مثلاً گالری تصاویر، مرتب‌سازی یا مدیریت جداگانه):

```javascript
Product
{
  _id: 1,
  name: "iPhone 15"
}


Image
{
  productId: 1,
  url: "front.jpg"
}
```

در این حالت تصاویر به صورت جدا ذخیره می‌شوند.

### نتیجه:

> اگر داده فقط در کنار Parent استفاده می‌شود ← `Embedding`
> اگر داده نیاز به جستجو، مدیریت یا استفاده مستقل دارد ← `Referencing`

---

### 4. انواع تکنیک‌های ارجاع (`Referencing Types`)

اگر طبق فریم‌ورک بالا تصمیم گرفتید که داده‌ها را جدا کنید (`Reference`)، باید یکی از 3 روش زیر را پیاده‌سازی کنید:

#### 1. ارجاع فرزند (`Child Referencing`)

پدر، لیستی از شناسه (`ID`) فرزندانش را نگه می‌دارد.

- _کاربرد:_ ارتباطات 1-به-چندِ محدود (مانند پستی که آرایه‌ای از آیدیِ تگ‌هایش را دارد).
- _نکته امنیتی:_ آرایه‌ها در MongoDB هرگز نباید تا بی‌نهایت رشد کنند.

#### 2. ارجاع پدر (`Parent Referencing`) ⭐️

پدر هیچ اطلاعی از فرزندان ندارد. این فرزند است که شناسه پدر را در خود نگه می‌دارد.

- _کاربرد:_ ارتباطات 1-به-بی‌نهایت (مثل میلیاردها لاگِ سرور که فقط آیدیِ سرور را در خود ذخیره می‌کنند).
- _مزیت:_ هیچ آرایه‌ای وجود ندارد که بزرگ شود، در نتیجه محدودیت 16 مگابایتی هرگز نقض نخواهد شد.

#### 3. ارجاع دوطرفه (`Two-way Referencing`)

هم پدر شناسه فرزندان را دارد، هم فرزند شناسه پدر را.

- _کاربرد:_ ارتباطات چند-به-چند (`Many-to-Many`).
- _مزیت:_ جستجو از هر دو طرف (پیدا کردن محصولاتِ یک دسته، یا پیدا کردن دسته‌های یک محصول) بی‌نهایت سریع می‌شود.

## ادامه فصل اول: طراحی معماری پایگاه داده پروژه 🏗️ (`Architecture Blueprint`)

در این فصل، تئوری‌های مدلسازی داده را روی پروژه واقعی (سیستم رزرو تورهای طبیعت‌گردی) پیاده‌سازی می‌کنیم. اپلیکیشن ما از 5 موجودیت اصلی تشکیل شده است:

- 🏕️ **تورها** (`Tours`)
- 👤 **کاربران** (`Users`)
- ⭐ **نظرات** (`Reviews`)
- 📍 **مکان‌ها** (`Locations` - ایستگاه‌های توقف هر تور)
- 💳 **خریدها** (`Bookings` - رزروهای انجام شده)

> 🎯 **هدف معماری:** طراحی این دیتابیس بر اساس قوانین طلاییِ پرفورمنس (`Performance`) و جلوگیری از کرش کردنِ سرور به دلیل رشد نامحدودِ داکیومنت‌ها (عبور از مرز 16MB) مهندسی شده است.

---

### 🗺️ دیاگرام بصری ارتباطات در دیتابیس

در نمودار زیر، فلش‌ها `──>` نشان می‌دهند که **کدام موجودیت، آیدیِ (`ObjectId`) موجودیت دیگر را در خود ذخیره کرده است**. (خطوط دوگانه `══>` نشان‌دهنده‌ی جاسازی کامل است).

```text
1. Reviews (Parent Referencing)
   [ ⭐ Review ] ──(user_id)──> [ 👤 User ]
   [ ⭐ Review ] ──(tour_id)──> [ 🏕️ Tour ]

2. Bookings (Parent Referencing + Intermediate)
   [ 💳 Booking ] ──(user_id)──> [ 👤 User ]
   [ 💳 Booking ] ──(tour_id)──> [ 🏕️ Tour ]

3. Guides (Child Referencing)
   [ 🏕️ Tour ] ──(guides: [id1, id2])──> [ 👤 Guides (Users) ]

4. Locations (Embedding)
   [ 🏕️ Tour ] ══(Embeds complete data)══> [ 📍 Locations ]

```

---

### 📊 استراتژی‌های پیاده‌سازی (Architecture Strategy)

بر اساس فریم‌ورک تصمیم‌گیری در MongoDB، معماری ارتباطات به شکل زیر مهندسی شده است:

🔹 **1. کاربران ⇄ نظرات** (`Users & Reviews`)

- **نوع ارتباط:** 1 به چند (`One-to-Many`)
- **نوع پیاده‌سازی:** ارجاع پدر (`Parent Referencing`)
- 🎯 **دلیل:** یک کاربر ممکن است در طول زمان هزاران نظر بنویسد. برای جلوگیری از رشد نامحدود آرایه‌ها و همچنین امکان جستجوی مستقلِ نظرات، شناسه کاربر مستقیماً در خودِ نظر ذخیره می‌شود.

🔹 **2. تورها ⇄ نظرات** (`Tours & Reviews`)

- **نوع ارتباط:** 1 به چند (`One-to-Many`)
- **نوع پیاده‌سازی:** ارجاع پدر (`Parent Referencing`)
- 🎯 **دلیل:** یک تور می‌تواند ده‌ها هزار نظر داشته باشد. برای جلوگیری از نقض محدودیت حجم 16 مگابایتیِ دیتابیس، داکیومنتِ تور باید کاملاً از نظرات ایزوله بماند.

🔹 **3. تورها ⇄ مکان‌ها** (`Tours & Locations`)

- **نوع ارتباط:** چند به چندِ محدود (`Few-to-Few`)
- **نوع پیاده‌سازی:** اِمبِد کردن (`Embedding`)
- 🎯 **دلیل:** تعداد ایستگاه‌های یک تور بسیار کم است (نهایتاً 5 مکان) و به جستجوی مستقلِ آن‌ها نیازی نداریم. برای لودِ آنی و سریعِ نقشه در سمت فرانت‌اند، این داده‌ها مستقیماً داخل تور جاسازی می‌شوند.

🔹 **4. تورها ⇄ راهنماها** (`Tours & Tour Guides`)

- **نوع ارتباط:** چند به چندِ محدود (`Few-to-Few`)
- **نوع پیاده‌سازی:** ارجاع فرزند (`Child Referencing`)
- 🎯 **دلیل:** راهنماها در واقع همان «کاربران» هستند که پروفایلشان (ایمیل، پسورد و...) مدام آپدیت می‌شود. اِمبِد کردن آن‌ها باعث می‌شد با هر تغییرِ پروفایل، مجبور به ویرایشِ داکیومنتِ تمام تورها باشیم.

🔹 **5. کاربران ⇄ خریدها ⇄ تورها** (`Bookings`)

- **نوع ارتباط:** 1 به چند (از هر دو طرف)
- **نوع پیاده‌سازی:** کالکشن واسط (`Intermediate Collection`)
- 🎯 **دلیل:** برای ثبت دقیق سوابق مالی (مثل مبلغ پرداخت‌شده در لحظه خرید و تاریخ دقیق تراکنش)، به یک موجودیت واسط نیاز داریم تا داکیومنت‌های تور و کاربر با داده‌های نامربوط شلوغ نشوند.

### 💡 نکات برجسته معماری (`Design Highlights`)

🛡️ **1. قرنطینه کردن نظرات (`Reviews Isolation`)**
نظرات به دلیل پتانسیلِ رشدِ بی‌نهایت، به ایزوله‌ترین بخشِ دیتابیس تبدیل شده‌اند. داکیومنتِ تور و کاربر کاملاً از نظراتشان بی‌خبرند و این ارتباط فقط از سمتِ کالکشن `Review` ردیابی می‌شود.

⚡ **2. استفاده هوشمندانه از اِمبِدینگ (`Embedding`)**
تنها موجودیتی که در این پروژه `Embed` شد، ایستگاه‌های تور (`Locations`) بود. این تصمیمِ استراتژیک باعث می‌شود کاربر به محض باز کردن صفحه تور، موقعیت‌های روی نقشه را بدون حتی یک میلی‌ثانیه تاخیر (و بدون نیاز به کوئریِ دوم) مشاهده کند.

🔄 **3. مدیریت هوشمند نقش‌ها (`Tour Guides`)**
با وجود اینکه ارتباط راهنماها و تورها از نوع `Few-to-Few` است (که ذاتاً کاندیدِ خوبی برای اِمبِد شدن است)، اما به دلیل ماهیتِ کاربریِ راهنماها (نیاز مکرر به لاگین کردن و تغییر مشخصات شخصی)، آیدیِ آن‌ها در قالب یک آرایه داخل داکیومنتِ تور (`Child Referencing`) ذخیره شد تا استقلالشان حفظ شود.

## فصل دوم: پیاده‌سازی داده‌های مکانی (`Geospatial-Data`) در `MongoDB`

در این بخش از توسعه بک‌اند، وارد دنیای هیجان‌انگیز داده‌های جغرافیایی می‌شویم. پایگاه داده `MongoDB` به صورت `Out-of-the-Box` از این نوع داده‌ها پشتیبانی می‌کند و به ما اجازه می‌دهد موقعیت‌های مختلف روی کره زمین را با استفاده از طول و عرض جغرافیایی مدل‌سازی کنیم.

> 💡 **نکته طلایی:** در استاندارد `GeoJSON`، ترتیب مختصات با سرویس‌هایی مثل `Google-Maps` کاملاً متفاوت (و تا حدی برعکس) است. شما باید همیشه ابتدا طول جغرافیایی (`Longitude` - محور افقی) و سپس عرض جغرافیایی (`Latitude` - محور عمودی) را وارد کنید.

### 1. هندسه‌های پشتیبانی‌شده در `GeoJSON`

برای ذخیره داده‌های مکانی در `MongoDB`، از یک فرمت استاندارد به نام `GeoJSON` استفاده می‌کنیم. این استاندارد به ما اجازه می‌دهد فراتر از مختصات ساده عمل کنیم:

🔹 **1. نقطه (`Point`):**

- _مثال واقعی:_ محل دقیق شروع یک تور مسافرتی، مکان یک رستوران یا موقعیت لحظه‌ای یک راننده.

🔹 **2. خط (`Line` / `LineString`):**

- _مثال واقعی:_ مسیر حرکت یک قطار، یک رودخانه یا جاده بین دو شهر.

🔹 **3. چندضلعی (`Polygon` / `MultiPolygon`):**

- _مثال واقعی:_ مرزهای جغرافیایی یک کشور، یک منطقه حفاظت‌شده جنگلی یا محدوده مجاز برای ارسال کالا.

---

### 2. نبرد بزرگ: آبجکت ساده در برابر آرایه

ما در مدل تور (`Tour`) دو فیلد مجزا برای مکان‌ها داریم. نحوه تعریف این دو فیلد تفاوت‌های بنیادینی در رفتار دیتابیس ایجاد می‌کند:

| ایستگاه‌های تور (`locations`)             | محل شروع تور (`startLocation`)                 | ویژگی                   |
| ----------------------------------------- | ---------------------------------------------- | ----------------------- |
| آرایه‌ای از آبجکت‌ها (`Array-of-Objects`) | یک آبجکت ساده (`Embedded-Object`)              | **نوع ساختار**          |
| بله 🟢 (`Mongoose`ساخته شده توسط )        | خیر 🔴 (فقط یک فیلد ساده است)                  | **تولید شناسه (`_id`)** |
| مستقل مدیریت می شودsub-documentبه عنوان   | به عنوان یک فیلد تودرتو و معمولی شناخته می‌شود | **ماهیت در دیتابیس**    |
| دارای فیلد `day` (روز بازدید از ایستگاه)  | بدون نیاز به فیلد زمان‌بندی                    | **فیلدهای اختصاصی**     |

---

### 3. فریم‌ورک پیاده‌سازی (چگونه `GeoJSON` را تعریف کنیم؟)

برای اینکه موتور پایگاه داده یک آبجکت را به عنوان داده مکانی معتبر بشناسد، حتماً باید 2 ویژگی اصلی را در سطح اسکیما (`Schema`) پیاده‌سازی کنیم:

🎯 **ویژگی اول: نوع هندسه (`type`)**

- این فیلد باید حتماً از نوع `String` باشد.
- برای جلوگیری از ثبت اشکال نامعتبر، از ویژگی `enum` استفاده کرده و آن را تنها روی مقدار `Point` قفل می‌کنیم.

🎯 **ویژگی دوم: آرایه مختصات (`coordinates`)**

- باید به شکل `[Number]` تعریف شود که نشان‌دهنده یک آرایه عددی است (همان طول و عرض جغرافیایی).

📝 **فیلدهای تکمیلی و اختیاری:**
در کنار موارد اجباری، می‌توانیم فیلدهای دیگری مثل آدرس (`address`) و توضیحات (`description`) را به صورت `String` اضافه کنیم تا اطلاعات معناداری به کلاینت (سمت فرانت‌اند) ارسال شود.

---

### 4. طراحی معماری مکان‌ها در پروژه 🏗️ (`Locations Architecture`)

در این بخش، تئوری‌های بالا را روی مدل اصلی پروژه یعنی تورها (`Tours`) پیاده‌سازی می‌کنیم. تصمیم معماری ما در اینجا، استفاده کامل از الگوی اِمبِد کردن (`Embedding` / `Denormalization`) است.

> 🎯 **هدف معماری:** ایجاد یک رابطه مستحکم بین تورها و مکان‌ها، به طوری که تمام مختصات جغرافیایی یک مسافرت، بدون نیاز به کوئری‌های سنگینِ اضافی و کاملاً یکجا برای لود شدن روی نقشه آماده باشند.

#### 🗺️ دیاگرام بصری ارتباطات مکانی در دیتابیس

در این ساختار، هیچ کالکشن مجزایی برای مکان‌ها وجود ندارد و تمام داده‌ها مستقیماً داخل داکیومنت والد (`Parent Document`) تزریق می‌شوند. (خطوط دوگانه `══>` نشان‌دهنده‌ی جاسازی کامل یا embedding است).

```text
Tour Model (Embedding Strategy)

   [ 🏕️ Tour ] ══(Embedded Object)══> [ 📍 startLocation ]

   [ 🏕️ Tour ] ══(Embedded Array)═══> [ 📍 locations (Sub-Documents) ]
                                          ├── { _id: 1, day: 1, type: "Point" }
                                          ├── { _id: 2, day: 3, type: "Point" }
                                          └── { _id: 3, day: 5, type: "Point" }

```

### 5. استراتژی‌های پیاده‌سازی (`Architecture Strategy`)

🔹 **1. محل شروع (`startLocation`)**

- **نوع ارتباط:** 1 به 1 (`One-to-One`)
- **نوع پیاده‌سازی:** اِمبِد کردنِ آبجکت (`Object Embedding`)
- 🎯 **دلیل:** هر تور دقیقاً یک نقطه شروع دارد که کاملاً به هویتِ همان تور گره خورده است و ما هیچ‌گاه نیازی نداریم نقاط شروع را به صورت مستقل از تورها جستجو کنیم.

🔹 **2. ایستگاه‌های مسیر (`locations`)**

- **نوع ارتباط:** 1 به چندِ محدود (`One-to-Few`)
- **نوع پیاده‌سازی:** اِمبِد کردن در قالب آرایه (`Array of Sub-Documents`)
- 🎯 **دلیل:** تعداد ایستگاه‌های یک مسافرت بسیار محدود است (نهایتاً 5 تا 10 توقفگاه). با قرار دادن این آبجکت‌ها در یک آرایه، `Mongoose` به طور خودکار به هر ایستگاه یک `ObjectId` اختصاص می‌دهد که هویت مستقلی در داخل داکیومنت تور به آن‌ها می‌بخشد.

---

### 6. نکات برجسته معماری 💡 (`Design Highlights`)

🛡️ **1. انعطاف‌پذیری فیلدها (`Data Flexibility`)**
در اسکیما، هیچ‌کدام از فیلدهای مکانی را با `required: true` محدود نکردیم. این استراتژی به ما اجازه می‌دهد تورهایی که هنوز برنامه‌ریزی مکانی دقیقی ندارند، بدون ایجاد خطا در دیتابیس ذخیره شوند.

⚡ **2. آمادگی برای کوئری‌های پیشرفته (`Geospatial Queries`)**
با استانداردسازی دقیق این داده‌ها، معماری ما اکنون آماده اجرای عملیات‌های سنگین مکانی است. در آینده می‌توانیم قابلیت‌هایی شگفت‌انگیز مثل پیدا کردن تمام تورهایی که در فاصله نزدیکِ کاربر قرار دارند را با پرفورمنس خیره‌کننده‌ای پیاده‌سازی کنیم.

🔄 **3. تزریق داده‌های جامع (`Data Seeding`)**
برای اینکه معماری جدید را تست کنیم، فایل‌های دیتای ساده (مثل `tours-simple`) کنار گذاشته شده و اسکریپت ایمپورت ما از این به بعد داده‌های جامعی را که شامل آرایه‌های پیچیده `locations` هستند به صورت کامل در `MongoDB` ذخیره خواهد کرد.

## فصل سوم: مدیریت ارتباطات داده‌ای راهنماها (`Tour-Guides`)

در این فصل از توسعه معماری پایگاه داده، به بررسی نحوه برقراری ارتباط بین تورها (`Tours`) و راهنماهای تور (`Users`) می‌پردازیم. ما دو رویکرد متفاوت یعنی `Embedding` (جاسازی) و `Referencing` (ارجاع‌دهی) را بررسی کرده و بهترین معماری را برای این سناریو پیاده‌سازی می‌کنیم.

---

### 1. بررسی تکنیک جاسازی (`Embedding`) و چالش‌های آن

در این روش، ایده این است که هنگام ایجاد یک تور جدید، کاربر صرفاً یک آرایه از شناسه‌های (`ID`) راهنماها را ارسال کند و ما در بک‌اند، داکیومنت‌های کاملِ آن کاربران را از دیتابیس دریافت کرده و مستقیماً داخل داکیومنتِ تور ذخیره (`Embed`) کنیم.

#### 💻 پیاده‌سازی موقت در `Middleware`:

برای درک این حالت، می‌توان از یک `Middleware` در سطح `Pre-Save` استفاده کرد:

```javascript
tourSchema.pre('save', async function (next) {
  const guidesPromises = this.guides.map(async (id) => await User.findById(id));
  this.guides = await Promise.all(guidesPromises);
  next();
});
```

🔹 **تحلیل فرآیند:** متد `map` روی آرایه `guides` لوپ می‌زند. چون عملیات جستجو در دیتابیس `Asynchronous` است، خروجیِ این حلقه صرفاً یک آرایه از `Promise` ها خواهد بود.
🔹 **مدیریت همزمانی (`Concurrency`):** برای حل این مشکل، با استفاده از `Promise.all` تمامی درخواست‌ها به صورت همزمان اجرا می‌شوند تا داکیومنت‌های واقعی دریافت و ذخیره شوند.

> 🛑 **نکته طلایی و دلیل توقف این رویکرد:** در سناریوی `Tour-Guides`، اگر یک راهنما آدرس ایمیل خود را تغییر دهد یا نقش او از `guide` به `lead-guide` ارتقا یابد، ما مجبور می‌شویم تمام تورهایی که این شخص در آن‌ها حضور دارد را پیدا کرده و یک‌به‌یک آپدیت کنیم! این کار پرفورمنس سرور را در عملیات آپدیت به شدت کاهش می‌دهد.

---

### 2. مقایسه استراتژی‌ها برای راهنماهای تور

با توجه به چالش‌های بالا، مقایسه زیر نشان می‌دهد که چرا رویکرد ارجاع‌دهی انتخاب بهتری است:

| ارجاع‌دهی (`Referencing`) ✅                     | جاسازی (`Embedding`) ❌                            | ویژگی                         |
| ------------------------------------------------ | -------------------------------------------------- | ----------------------------- |
| ذخیره شناسه (`ObjectId`) در آرایه                | آپدیت کامل داکیومنت کاربر و ذخیره آن در آرایه تور  | **ساختار ذخیره‌سازی**         |
| نیازی به آپدیت تورها نیست (کاملاً مستقل)         | باید تمام تورهای مرتبط جستجو و یک‌به‌یک آپدیت شوند | **هنگام تغییر مشخصات راهنما** |
| 🚀 بسیار بالا (بدون نیاز به آپدیت‌های زنجیره‌ای) | 🐢 به شدت پایین (فشار سنگین به موتور دیتابیس)      | **پرفورمنس آپدیت (`Update`)** |
| نیازمند تکنیک `Populating` برای نمایش            | آماده نمایش بدون نیاز به کوئری دوم                 | **سرعت خواندن (`Read`)**      |

---

### 3. پیاده‌سازی ارجاع‌دهی (`Referencing`)

به دلیل حفظ پرفورمنس، موجودیت‌های تورها (`Tours`) و کاربران (`Users`) را به عنوان دو کالکشن (`Collection`) کاملاً ایزوله نگه می‌داریم و صرفاً شناسه‌های آن‌ها را به یکدیگر متصل می‌کنیم.

#### 🏛️ دیاگرام معماری ارجاعی (`Reference-Architecture`)

```text
+------------------------------------+          +------------------------------------+
| Collection: `tours`                |          | Collection: `users`                |
+------------------------------------+          +------------------------------------+
| Document: `Tour`                   |          | Document: `User`                   |
|                                    |          |                                    |
|  name: "Forest Hiker",             |          |  _id: ObjectId("5c8a1d5b..."),     |
|  guides: [                         | ==ref==> |  name: "John Doe",                 |
|    ObjectId("5c8a1d5b..."),        |          |  role: "lead-guide"                |
|    ObjectId("5c8a22c6...")         |          |                                    |
|  ]                                 |          +------------------------------------+
+------------------------------------+

```

---

### 4. پیکربندی `Referencing` در `Mongoose`

برای پیاده‌سازی این معماری، باید نوع فیلد `guides` را در اسکیما (`Schema`) تغییر دهیم تا دیتابیس متوجه شود با شناسه‌های معتبر روبه‌رو است، نه رشته‌های متنی ساده:

🎯 **نوع داده (`type`):**
باید دقیقاً برابر با `mongoose.Schema.ObjectId` تنظیم شود (دقت کنید که حرف `O` حتماً باید بزرگ باشد).
🔗 **هدف ارجاع (`ref`):**
با کلمه کلیدی `ref`، به `Mongoose` اعلام می‌کنیم که این شناسه‌ها متعلق به مدل `User` هستند.

```javascript
const mongoose = require('mongoose');

// ... درون فایل tourSchema ...
  guides: [
    {
      type: mongoose.Schema.ObjectId,
      ref: 'User',
    },
  ],
// ...

```

> 🛡️ **نکته معماری:** در این رویکرد، به هیچ وجه نیازی به `Import` کردن مدل `User` در فایل مدل تور نداریم. ویژگی `ref` به صورت پس‌زمینه (`Behind-the-Scenes`) این ارتباط را برای موتور دیتابیس شفاف و مدیریت می‌کند.

---

### 5. خروجی در `Postman` و قدم بعدی (`Next-Step`)

با ارسال درخواست ساخت تور جدید، مشاهده می‌کنید که در فیلد `guides` تنها شناسه‌های `ObjectId` ذخیره می‌شوند.
در مرحله بعدی، با استفاده از تکنیکی قدرتمند به نام `Populating`، این شناسه‌ها را دقیقاً در لحظه اجرای کوئری با داده‌های واقعی جایگزین خواهیم کرد تا در خروجیِ `API` اطلاعات کامل راهنماها به کاربر نمایش داده شود.

## فصل سوم: پیاده‌سازی `Populate` و استخراج داده‌های ارجاعی

در بخش قبلی، با ایجاد یک ارجاع (`Reference`) در فیلد `guides` واقع در مدل تور، ارتباط بین دو مجموعه داده را برقرار کردیم. اکنون برای درک بهتر منطق بک‌اند، به بررسی نحوه استخراج این داده‌ها می‌پردازیم. برای دسترسی به اطلاعات راهنماهای تور در زمان اجرای کوئری، از فرآیندی به نام `populate` استفاده می‌کنیم.

---

### ۱. مفهوم و عملکرد `Populate`

متد `populate` مقادیر ارجاع‌داده‌شده (شناسه‌ها) را با داده‌های واقعی و مرتبط جایگزین می‌کند.

- نتیجه این عملیات به گونه‌ای به نظر می‌رسد که گویی داده‌ها از ابتدا درون داکیومنت جاسازی (`Embedded`) شده‌اند، در حالی که در واقعیت در یک کالکشن کاملاً متفاوت قرار دارند.

- باید به خاطر داشته باشید که فرآیند `populate` فقط در سطح کوئری انجام می‌شود و تغییری در داده‌های ذخیره‌شده در پایگاه داده ایجاد نمی‌کند.

---

### ۲. فیلتر کردن فیلدهای خروجی (انتخاب داده‌های خاص)

گاهی اوقات ما به تمام اطلاعات یک داکیومنت مرجع نیازی نداریم. به عنوان مثال، ویژگی‌هایی مانند `__v` یا `passwordChangedAt` در مدل کاربران، اطلاعاتی نیستند که بخواهیم در خروجی تورها نمایش دهیم.

برای حل این مسئله، به جای ارسال یک رشته متنی ساده به متد `populate`، می‌توانیم یک آبجکت شامل تنظیمات زیر را ارسال کنیم:

- **ویژگی `path`:** نام فیلدی است که می‌خواهیم با داده‌های واقعی پر شود (در اینجا فیلد `guides`).
- **ویژگی `select`:** از این تنظیم برای حذف فیلدهای نامطلوب استفاده می‌شود؛ به این صورت که نام آن‌ها را همراه با یک علامت منفی (`-`) وارد می‌کنیم.

---

### ۳. مدیریت کدهای تکراری با `Query Middleware`

اگر بخواهیم `populate` را هم در هندلر مربوط به دریافت یک تور (`getTour`) و هم در دریافت همه تورها (`getAllTours`) بنویسیم، دچار مشکل کدهای تکراری (`Duplicate Code`) می‌شویم.
راه‌حل بهتر و تمیزتر در معماری بک‌اند، استفاده از **`Query Middleware`** است.

با استفاده از یک عبارت منظم (`Regular Expression`) مانند `/^find/`، می‌توانیم میدل‌وری بنویسیم که به صورت خودکار روی تمامی کوئری‌هایی که با کلمه `find` شروع می‌شوند (مانند `findById`، `find` و `findByIdAndUpdate`) اجرا شود.

#### 💻 پیاده‌سازی در فایل مدل (Schema)

با قرار دادن کد زیر در فایل مدل تور، فیلد `guides` به صورت خودکار در تمامی کوئری‌های جستجو با داده‌های کاربر جایگزین می‌شود:

```javascript
tourSchema.pre(/^find/, function (next) {
  // کلمه کلیدی this در Query Middleware به کوئری فعلی اشاره دارد
  this.populate({
    path: 'guides',
    select: '-__v -passwordChangedAt',
  });

  next();
});
```

---

### ۴. ملاحظات عملکردی (Performance)

به عنوان یک توسعه‌دهنده، درک جریان داده‌ها در پس‌زمینه (`Behind the scenes`) بسیار مهم است.

- استفاده از `populate` در واقع باعث ایجاد و اجرای یک کوئری جدید در پایگاه داده می‌شود تا بتواند اطلاعات تورها و کاربران را به صورت همزمان دریافت کند.
- در برنامه‌های کوچک، این افت عملکرد جزئی کاملاً بی‌اهمیت است.
- با این حال، در برنامه‌های بسیار بزرگ که در آن‌ها از تعداد زیادی `populate` در بخش‌های مختلف استفاده می‌شود، این موضوع می‌تواند بر روی عملکرد کلی سیستم تأثیرگذار باشد.

---

### ۵. خلاصه منطق ارتباط داده‌ها در دو گام

این ابزار یکی از بنیادی‌ترین مفاهیم برای کار با داده‌های مرتبط در `Mongoose` است و منطق آن در دو گام ساده خلاصه می‌شود:

۱. ابتدا یک ارجاع (`Reference`) به یک مدل دیگر ایجاد می‌کنید تا ارتباط بین دو مجموعه داده شکل بگیرد.

۲. سپس با استفاده از متد `populate`، فیلد مشخص‌شده را با داده‌های واقعی پر می‌کنید.

### فصل چهارم: پیاده‌سازی مدل نظرات (`Review Model`)

در این بخش، نحوه ترجمه مدل داده‌ای به کدهای واقعی و پیاده‌سازی مدل نظرات (`Reviews Model`) بررسی می‌شود.

### ۱. ساختار فایل و مدل نظرات

برای شروع، یک فایل جدید به نام `reviewModel.js` در پوشه `models` ایجاد می‌کنیم. فیلدهای اصلی و پایه‌ای این مدل به شرح زیر است:

- 🔹 **فیلد متن نظر (`review`):** از نوع `String` بوده و به دلیل اینکه متن نظر نمی‌تواند خالی باشد، به صورت الزامی (`required`) تعریف می‌شود.

- 🔹 **فیلد امتیاز (`rating`):** از نوع `Number` بوده و با استفاده از اعتبارسنج‌های ساده، مقدار حداقل (`min`) روی 1 و مقدار حداکثر (`max`) روی 5 تنظیم می‌شود.

- 🔹 **فیلد تاریخ ایجاد (`createdAt`):** از نوع `Date` بوده و مقدار پیش‌فرض آن روی `Date.now` تنظیم می‌شود.

---

### ۲. پیاده‌سازی ارجاع‌پدری (`Parent Referencing`)

برای اتصال نظرات به تورها و کاربران، از الگوی ارجاع‌پدری استفاده می‌کنیم؛ زیرا هر دو مدل تور و کاربر والد این مجموعه داده محسوب می‌شوند:

- 🔹 **ارجاع به تور (`tour`):** از نوع `mongoose.Schema.ObjectId` بوده، مرجع آن مدل `Tour` است و به عنوان یک مقدار الزامی تعریف می‌شود.

- 🔹 **ارجاع به کاربر (`user`):** از نوع `mongoose.Schema.ObjectId` بوده، مرجع آن مدل `User` است و به عنوان نویسنده نظر الزامی می‌باشد.

> 💡 **نکته کلیدی:** در تعریف `ObjectId` دقت کنید که حروف `Object` و `Id` با حروف بزرگ و حرف `d` به صورت کوچک نوشته شود تا از خطاهای رایج جلوگیری گردد.

---

### ۳. تنظیمات اسکیما و خروجی‌های مجازی (`Virtuals`)

برای اینکه ویژگی‌های مجازی (فیلدهایی که در دیتابیس ذخیره نمی‌شوند اما محاسبه می‌شوند) در خروجی‌های `JSON` و آبجکت‌ها نمایش داده شوند، گزینه‌های مربوطه به اسکیما اضافه می‌شوند:

```typescript
const mongoose = require('mongoose');
const Tour = require('./tourModel');

const reviewSchema = new mongoose.Schema(
  {
    review: {
      type: String,
      required: [true, 'Review can not be empty!'],
    },
    rating: {
      type: Number,
      min: 1,
      max: 5,
    },
    createdAt: {
      type: Date,
      default: Date.now,
    },
    tour: {
      type: mongoose.Schema.ObjectId,
      ref: 'Tour',
      required: [true, 'Review must belong to a tour.'],
    },
    user: {
      type: mongoose.Schema.ObjectId,
      ref: 'User',
      required: [true, 'Review must belong to a user'],
    },
  },
  {
    toJSON: { virtuals: true },
    toObject: { virtuals: true },
  },
);
const Review = mongoose.model('Review', reviewSchema);
module.exports = Review;
```

---

### ۴. نکات کلیدی و تله‌های معماری (`Key Points & Pitfalls`)

- 🔹 **انتخاب الگو (`Parent Referencing vs Embedded`):** چرا از ارجاع‌پدری استفاده شد؟ چون حجم نظرات نامشخص است و با رشد اپلیکیشن ممکن است بسیار زیاد شود؛ ذخیره آرایه‌های غول‌پیکر از نظرات درون مدل والد یک اشتباه معماری مرگبار است.

- 🔹 **تله املایی در `ObjectId`:** حساسیت بزرگ و کوچک بودن حروف در `mongoose.Schema.ObjectId` (حرف `d` کوچک و بقیه بزرگ) از خطاهای رایجی است که می‌تواند ساعت‌ها برنامه‌نویس را درگیر عیب‌یابی کند.

- 🔹 **محدودیت اعتبارسنج‌ها (`Validators`):** متدهای اعتبارسنجی ساده مانند `min` و `max` فقط برای داده‌های از نوع عددی (`Number`) در `Mongoose` کارایی دارند.

- 🔹 **پیکربندی خروجی‌ها (`JSON & Object Outputs`):** تنظیمات `toJSON` و `toObject` با مقدار `{ virtuals: true }` تضمین می‌کند که فیلدهای محاسباتی و مجازی حتماً در خروجی نهایی داده‌ها به کاربر نمایش داده شوند.

### ۱. پیاده‌سازی کنترلر (`controllers/reviewController.js`)

- 🔹 **متد دریافت نظرات (`getAllReviews`):** فراخوانی `Review.find()` برای دریافت تمام نظرات و ارسال خروجی با کد 200.
- 🔹 **متد ایجاد نظر (`createReview`):** دریافت داده‌ها از `req.body` و ذخیره با `Review.create()` با کد 201.

```javascript
const Review = require('../models/reviewModel');
const catchAsync = require('./../utils/catchAsync');

exports.getAllReviews = catchAsync(async (req, res, next) => {
  const reviews = await Review.find();

    status: 'success',
    results: reviews.length,
    data: { reviews },
  });
});

exports.createReview = catchAsync(async (req, res, next) => {
  const newReview = await Review.create(req.body);

  res.status(201).json({
    status: 'success',
    data: { review: newReview },
  });
});
```

### فصل پنجم: پیاده‌سازی عملیات Populate برای نظرات (Reviews)

در این بخش، قصد داریم داکیومنت‌های مربوط به نظرات (`Reviews`) را به گونه‌ای تنظیم کنیم که هر زمان کوئری روی آن‌ها اجرا شد، اطلاعات مربوط به تور (`Tour`) و کاربر (`User`) به صورت خودکار واکشی (`Populate`) شوند.

> 💡 **نکته طلایی:** زمانی که می‌خواهید بیش از یک فیلد را در یک کوئری مقداردهی (`Populate`) کنید، باید متد `populate` را به ازای هر فیلد، به صورت زنجیره‌ای (پشت سر هم) فراخوانی کنید.

### 💻 کدهای پیاده‌سازی میدل‌ور

برای خودکارسازی این فرآیند، از یک میدل‌ورِ `pre` روی اسکیما (`Schema`) استفاده می‌کنیم:

```javascript
reviewSchema.pre(/^find/, function (next) {
  this.populate({
    path: 'tour',
    select: 'name',
  }).populate({
    path: 'user',
    select: 'name photo',
  });
  next();
});
```

### 📊 تحلیل معماری و کدهای نوشته شده

🔹 **اجرای میدل‌ور `pre-find`:**
با استفاده از عبارت باقاعده (`Regex`) به شکل `/^find/`، به `Mongoose` دستور می‌دهیم که این میدل‌ور را قبل از اجرای تمام متدهایی که با کلمه `find` شروع می‌شوند (مثل `find` و `findOne`) اجرا کند.

🔹 **واکشی فیلد `tour`:**
در اولین فراخوانی `populate`، به اسناد مرتبط ارجاع می‌دهیم. برای جلوگیری از دریافت داده‌های اضافی و سنگین شدن کوئری، با استفاده از ویژگی `select` فقط فیلد نام (`name`) را استخراج می‌کنیم.

🔹 **واکشی فیلد `user`:**
در دومین فراخوانی `populate`، اطلاعات کاربری که نظر را ثبت کرده است واکشی می‌شود. در اینجا نیز صرفاً فیلدهای نام (`name`) و تصویر پروفایل (`photo`) را انتخاب می‌کنیم.

> 🛡️ **نکته امنیتی در Data Privacy:** در هنگام واکشی اطلاعات کاربران، هرگز فیلدهای حساسی مانند ایمیل (`email`) را انتخاب (`select`) نکنید. هیچ‌کس نباید به اطلاعات خصوصی کاربرانی که نظر ثبت کرده‌اند دسترسی داشته باشد تا از نشت داده‌ها (`Data Leaks`) به سمت کلاینت جلوگیری شود.

### 🗺️ دیاگرام جریان واکشی داده‌ها

```text
[ ⭐ Review Query ]
     │
     ├──(Populate 1)──> [ 🏕️ Tour Collection ] ──(Select)──> name
     │
     └──(Populate 2)──> [ 👤 User Collection ] ──(Select)──> name, photo

```

### ⚡ بررسی پرفورمنس (Performance Impact)

عملیات `Populate` در واقعیت جادو نمی‌کند؛ بلکه در پس‌زمینه، کوئری‌های مستقلی به دیتابیس ارسال می‌کند تا اسناد منطبق را پیدا کند.

- 🎯 **افزایش بار دیتابیس:** در معماری بالا، برای هر نظر، 2 کوئری اضافه در پس‌زمینه اجرا می‌شود.
- ⏱️ **تاخیر زمانی:** این رفت‌وآمدهای اضافه، زمان پاسخگویی سرور را افزایش می‌دهد (به عنوان مثال در تست‌های انجام شده، زمان درخواست از 157 میلی‌ثانیه به 266 میلی‌ثانیه افزایش یافت).
- ⚖️ **مقیاس‌پذیری:** افزایش زمان در حد 100 میلی‌ثانیه برای پروژه‌های کوچک فاجعه نیست، اما در سطح کلان (`Scale`) و ترافیک‌های بالا، طراحِ معماری باید این سربارِ پردازشی را به دقت مدنظر داشته باشد.

## فصل ششم: پیاده‌سازی ویژگی پیشرفته Virtual Populate در Mongoose

در این مرحله، ما نظرات (`Reviews`) را با اطلاعات تور (`Tour`) و کاربر (`User`) واکشی (`Populate`) کرده‌ایم. اما یک مشکل بزرگ هنوز حل نشده است: چگونه می‌توانیم وقتی یک تور خاص را جستجو می‌کنیم، به تمام نظراتِ ثبت‌شده برای آن تور دسترسی پیدا کنیم؟.

این مشکل به این دلیل به وجود می‌آید که ما از الگوی ارجاع پدر (`Parent Referencing`) برای نظرات استفاده کردیم. یعنی این نظرات هستند که به تورها اشاره می‌کنند، و تور هیچ اطلاعی از نظرات مربوط به خودش ندارد.

> 💡 **نکته طلایی:** در معماری ارجاع پدر، داکیومنت والد (`Parent`) هیچ‌گونه اطلاعاتی از فرزندان (`Children`) خود ندارد. در این پروژه نیز، اگرچه گاهی بی‌خبری والد مشکلی ایجاد نمی‌کند، اما اینجا نیاز داریم که تور از تمام نظراتش مطلع باشد.

### 🗺️ بررسی راه‌حل‌های موجود برای حل این چالش

برای اینکه تور بتواند نظرات خود را ببیند، چندین راه وجود دارد:

🔹 **راهکار اول (کوئری دستی):**

- **نحوه کار:** هر بار که درخواستی برای دریافت یک تور ارسال می‌شود، یک کوئری مجزا و دستی برای دریافت نظراتِ آن تور بنویسیم.

- **نتیجه:** این روش بسیار طاقت‌فرسا (`Cumbersome`) و غیراستاندارد است.

🔹 **راهکار دوم (ارجاع فرزند - Child Referencing):**

- **نحوه کار:** یک آرایه از شناسه‌های (`IDs`) تمام نظرات در داکیومنت تور ذخیره کنیم و سپس آن آرایه را `Populate` کنیم.

- **نتیجه:** ما در همان ابتدای کار این روش را رد کردیم؛ زیرا نمی‌خواهیم آرایه‌ای از شناسه‌ها بسازیم که به طور نامحدود در دیتابیس ما رشد کند. به همین دلیل بود که از ابتدا ارجاع پدر را انتخاب کردیم.

🎯 **راهکار طلایی (ویژگی Virtual Populate):**

- **نحوه کار:** فریم‌ورک `Mongoose` یک قابلیت بسیار پیشرفته و عالی به نام `Virtual Populate` ارائه می‌دهد.

- **نتیجه:** با این ویژگی، می‌توانیم بدون اینکه آرایه‌ای از شناسه‌ها را به صورت فیزیکی در دیتابیس ذخیره (`Persist`) کنیم، نظراتِ مربوط به یک تور را به دست آوریم. در واقع، این روش مشکلِ آرایه‌های نامحدودِ ارجاع فرزند را حل می‌کند و مانند ایجاد فیلدهای مجازی (`Virtual Fields`) عمل می‌کند، اما با قابلیت واکشی داده‌ها.

---

### 💻 گام 1: پیاده‌سازی Virtual Populate در اسکیما

برای راه‌اندازی این ارتباط مجازی، باید به فایل مدل تور (`Tour Model`) برویم و کدهای زیر را روی اسکیما (`Schema`) پیاده‌سازی کنیم:

```javascript
// Virtual populate
tourSchema.virtual('reviews', {
  ref: 'Review',
  foreignField: 'tour',
  localField: '_id',
});
```

**تحلیل دقیق پارامترهای اتصال:**
اتصال این دو دیتاست (`Data sets`) به یکدیگر، پیچیده‌ترین بخشِ پیاده‌سازی `Virtual Populate` است، پس باید آن را به دقت درک کنیم:

- پارامتر `ref`: نام مدلی را مشخص می‌کند که می‌خواهیم به عنوان هدف به آن ارجاع دهیم (در اینجا مدل `Review`).

- پارامتر `foreignField`: نام فیلدی در مدل خارجی (یعنی در مدل `Review`) است که شناسه مدل فعلی ما در آن ذخیره شده است. در مدل نظرات، فیلدی به نام `tour` وجود دارد که به تور فعلی اشاره می‌کند.

- پارامتر `localField`: نام فیلدی در مدل فعلی (یعنی مدل `Tour`) است که شناسه اصلی سیستم در آن قرار دارد. این مقدار همان `_id` تور است.

- خلاصه کارکرد: فیلد `_id` در مدل لوکال ما، با نامِ `tour` در مدل خارجی (`Review`) شناخته می‌شود.

---

### 💻 گام 2: واکشی داده‌ها در کنترلر (Controller)

حالا که اتصالِ مجازی برقرار شد، می‌توانیم دقیقاً مانند ارجاعاتِ واقعی، از متد `populate` استفاده کنیم.

> 🛡️ **نکته معماری:** ما فقط زمانی نظرات را `Populate` می‌کنیم که کاربر درخواست دریافت **یک تور خاص** (`getTour`) را داشته باشد. در درخواستِ دریافت همه تورها (`getAllTours`) نباید این کار را انجام دهیم؛ زیرا ارسالِ این حجم از اطلاعاتِ نظرات به سمت کلاینت بسیار زیاد است و برای ساخت صفحات مرور کلی (`Overview Page`) اصلاً نیازی به آن‌ها نداریم.

```javascript
exports.getTour = catchAsync(async (req, res, next) => {
  // اضافه کردن متد populate به انتهای کوئری
  const tour = await Tour.findById(req.params.id).populate('reviews');

  if (!tour) {
    return next(new AppError('No tour found with that ID', 404));
  }

  res.status(200).json({
    status: 'success',
    data: { tour },
  });
});
```

---

### ⚡ بهینه‌سازی پرفورمنس (حل مشکل زنجیره Populate)

با اجرای کدهای بالا، ما یک تور را به صورت کامل به همراه نظراتش دریافت می‌کنیم که نشان‌دهنده عملکرد صحیح `Virtual Populate` است. اما این فرآیند یک مشکل عملکردی (`Performance`) بزرگ ایجاد می‌کند: شکل‌گیریِ یک زنجیره از `Populate` های ناکارآمد.

**شرح مشکل زنجیره‌ای:**

- مرحله اول: ابتدا تور را با فیلد `reviews` واکشی می‌کنیم.

- مرحله دوم: هر نظر (`Review`) از قبل در میدل‌ورِ خود طوری تنظیم شده بود که اطلاعات تور (`Tour`) و کاربر (`User`) را مجدداً واکشی کند.

- مرحله سوم: تورها همچنین ممکن است اطلاعات راهنماها (`Guides`) را نیز واکشی کنند.

- نتیجه نهایی: نتیجه این می‌شود که تور حاوی نظرات است، نظرات دوباره حاوی اطلاعات همان تور هستند و این زنجیره تودرتو (شامل 3 واکشی همزمان) یک آشفتگیِ ناکارآمد ایجاد می‌کند.

**راه‌حل بهینه‌سازی:**
برای حل این مشکل، باید واکشیِ اطلاعاتِ تور را روی فیلدِ نظرات غیرفعال (`Turn off`) کنیم. بسته به نیاز اپلیکیشن، در این پروژه منطقی‌تر این است که نظرات روی تورها در دسترس باشند، اما ضروری نیست که اطلاعات کامل تور روی هر نظر وجود داشته باشد. بنابراین به فایل مدل `Review` می‌رویم و این بخش را کامنت می‌کنیم:

```javascript
reviewSchema.pre(/^find/, function (next) {
  // این واکشی را برای جلوگیری از زنجیره ناکارآمد کامنت می‌کنیم
  // this.populate({
  //   path: 'tour',
  //   select: 'name',
  // });

  this.populate({
    path: 'user',
    select: 'name photo',
  });
  next();
});
```

با انجام این کار، ما همچنان از ارجاع پدر (`Parent Referencing`) استفاده می‌کنیم و مدل نظر (`Review`) صرفاً شناسه (`ID`) تور را درون خود نگه می‌دارد، اما برای حفظ سرعت سیستم، دیگر آن را واکشی و به دیتای کامل تبدیل نمی‌کند.

## فصل هفتم: مسیرهای تودرتو (Nested Routes) و اتصال آن‌ها با Merge Params

در این فصل قصد داریم مسیرهای تودرتو (`Nested Routes`) را بررسی کنیم، متوجه شویم چرا به آن‌ها نیاز داریم و چگونه می‌توانیم با استفاده از ویژگی‌های پیشرفته در `Express` آن‌ها را به صورت بهینه و تمیز پیاده‌سازی کنیم.

### 1. مفهوم و کاربرد مسیرهای تودرتو

تا به اینجا، برای ایجاد یک نظر (`Review`) جدید، مجبور بودیم شناسه‌ی تور (`Tour ID`) و شناسه‌ی کاربر (`User ID`) را به صورت دستی در بدنه درخواست (`Request Body`) وارد کنیم. این روش برای تست در طول توسعه مناسب است، اما در دنیای واقعی یک ایده بد محسوب می‌شود.

در یک برنامه واقعی:

- 🔹 شناسه‌ی کاربر باید به صورت خودکار از کاربرِ در حالِ لاگین (`Logged-in User`) خوانده شود.

- 🔹 شناسه‌ی تور باید مستقیماً از داخل آدرسِ درخواست (`URL`) به دست آید.

اینجاست که مسیرهای تودرتو وارد عمل می‌شوند. وقتی بین دو منبع داده (`Resource`) ارتباط والد و فرزندی شفافی وجود دارد، استفاده از این مسیرها ضروری است (در اینجا نظرات فرزندِ تورها هستند).

**ساختار استاندارد مسیرهای تودرتو در API:**

```text
// POST request for a new review on a specific tour
POST /tours/234fad4/reviews

// GET request for all reviews on a specific tour
GET /tours/234fad4/reviews

// GET request for a specific review on a specific tour
GET /tours/234fad4/reviews/9488bca

```

مزیت بزرگ این ساختار این است که کاربرِ API فوراً ارتباط بین این منابع را درک می‌کند و دیگر نیازی به ارسال پارامترهای گیج‌کننده در کوئری‌استرینگ (`Query String`) نخواهد بود.

---

### 2. پیاده‌سازی اولیه (روش غیراستاندارد)

ابتدا باید کنترلر نظرات را برای پذیرش اطلاعات از URL و میدل‌ور احراز هویت، به‌روزرسانی کنیم.

> 💡 **نکته طلایی:** ما این امکان را همچنان حفظ می‌کنیم که اگر پارامترها در بادی درخواست وجود داشتند، از آن‌ها استفاده شود (این کار برای تست کردن عالی است)؛ وگرنه به صورت خودکار آن‌ها را از URL و کاربر لاگین‌شده پر می‌کنیم.

```javascript
// File: reviewController.js
exports.createNewReview = catchAsync(async (req, res, next) => {
  // Allow nested routes: Set tour ID from URL if not in body
  if (!req.body.tour) req.body.tour = req.params.tourId;

  // Allow nested routes: Set user ID from logged-in user if not in body
  if (!req.body.user) req.body.user = req.user.id;

  const newReview = await Review.create(req.body);
  // ...
});
```

در پیاده‌سازی اولیه، مسیر زیر را موقتاً داخل فایل روترِ تورها (`Tour Router`) ایجاد کردیم:

```javascript
// File: tourRoutes.js (Messy Implementation)
router
  .route('/:tourId/reviews')
  .post(
    authController.protect,
    authController.restrictTo('user'),
    reviewController.createNewReview,
  );
```

**مشکل این روش چیست؟**
با اینکه کد بالا کار می‌کند، اما نوشتن روت‌های مربوط به «نظرات» در داخل فایل روترِ «تورها»، کدها را کثیف و گیج‌کننده می‌کند (`Messy Implementation`). همچنین، این روش باعث کدهای تکراری می‌شود، زیرا در روترِ نظرات هم باید روتِ مشابهی داشته باشیم.

### 3. پیاده‌سازی پیشرفته و اصولی با `mergeParams`

برای حل این کثیفی، باید فایل روترها را از هم جدا کنیم و از یک قابلیت پیشرفته در Express به نام `mergeParams` کمک بگیریم.

#### مرحله اول: هدایت کردن درخواست‌ها از روتر تور به روتر نظرات

در فایل `tourRoutes.js`، به Express می‌گوییم هر زمان درخواستی دریافت کرد که با `/:tourId/reviews` شروع می‌شد، دیگر خودش آن را پردازش نکند، بلکه آن را مستقیماً به روترِ نظرات ارسال کند (`Mounting a Router`).

```javascript
// File: tourRoutes.js
const reviewRouter = require('./../routes/reviewRoutes');

// Mount the review router for this specific nested route
router.use('/:tourId/reviews', reviewRouter);
```

#### مرحله دوم: استفاده از `mergeParams` در روتر نظرات

به طور پیش‌فرض، هر روتر در Express فقط و فقط به پارامترهای URL خودش دسترسی دارد. به همین دلیل، روتر نظرات نمی‌تواند به پارامترِ `tourId` که در روترِ تورها تعریف شده است، دسترسی پیدا کند. برای ادغام این پارامترها و ارسال آن‌ها بین روترها، هنگام ساخت روتر، ویژگی `mergeParams` را روی `true` تنظیم می‌کنیم.

```javascript
// File: reviewRoutes.js
// Enable mergeParams to access tourId from the parent router (tourRouter)
const router = express.Router({ mergeParams: true });

router
  .route('/')
  .get(reviewController.getAllReviews)
  .post(
    authController.protect,
    authController.restrictTo('user'),
    reviewController.createNewReview,
  );

module.exports = router;
```

### 🎯 جمع‌بندی عملکرد این معماری جدید

اکنون فارغ از اینکه کلاینت به کدام یک از دو آدرس زیر درخواست `POST` بفرستد، سیستم ما دقیقاً یک عملکرد واحد را از یک فایل مشترک اجرا می‌کند و هیچ کد تکراری تولید نمی‌شود:

- 🔹 `POST /reviews/`
- 🔹 `POST /tours/234fad4/reviews/`

وقتی کلاینت به آدرس دوم درخواست می‌دهد، ابتدا روتر تورها (`Tour Router`) آن را دریافت کرده، `tourId` را شناسایی می‌کند و سپس آن را به روتر نظرات (`Review Router`) هدایت می‌کند. در آنجا، به لطفِ `mergeParams`، روتر نظرات می‌تواند شناسه تور را بخواند و آن را در کنترلر ذخیره کند.

---

## ادامه فصل هشتم: پیاده‌سازی مسیر تودرتو برای دریافت نظرات (Nested GET Endpoint)

در دو فصل گذشته، یک مسیر تودرتو (`Nested Route`) از نوع `POST` برای ایجاد نظرات روی یک تور مشخص ایجاد کردیم. اکنون قصد داریم این معماری را گسترش داده و یک مسیر از نوع `GET` برای دریافت نظراتِ یک تورِ خاص بسازیم.

در حال حاضر، کنترلر `getAllReviews` تمام نظراتِ موجود در دیتابیس را برمی‌گرداند. اما یکی از کاربردهای بسیار رایج در API این است که بخواهیم فقط نظراتِ یک تورِ مشخص را دریافت کنیم.

> 💡 **نکته طلایی:** به لطف قابلیت `mergeParams` و هدایتِ روترها که در فصل قبل پیاده‌سازی کردیم، تابع `getAllReviews` به صورت خودکار هر زمان که یک درخواست `GET` به مسیر تودرتو ارسال شود اجرا شده و به پارامتر `tourId` دسترسی خواهد داشت.

---

### 💻 کدهای پیاده‌سازی و تغییرات کنترلر

برای پیاده‌سازی این قابلیت، نیازی به کدهای پیچیده نیست؛ تنها باید تغییرات کوچکی در هندلر `getAllReviews` اعمال کنیم:

```javascript
exports.getAllReviews = catchAsync(async (req, res, next) => {
  let filter = {};

  // بررسی وجود شناسه تور و مقداردهی فیلتر
  if (req.params.tourId) filter = { tour: req.params.tourId };

  const reviews = await Review.find(filter);

  res.status(200).json({
    status: 'success',
    result: reviews.length,
    data: {
      reviews,
    },
  });
});
```

---

### 📊 تحلیل منطق کد (Logic Analysis)

- 🔹 متغیر `filter`: ابتدا یک متغیر خالی به نام `filter` تعریف می‌کنیم. اگر این مسیر به صورت عادی و غیر تودرتو (`Regular API Call`) فراخوانی شود، این شیء خالی می‌ماند و در نتیجه متد `find` تمام نظراتِ دیتابیس را پیدا می‌کند.

- 🔹 پارامتر `tourId`: با استفاده از یک شرط `if` بررسی می‌کنیم که آیا پارامتر `tourId` در درخواست ارسال شده است یا خیر.

- 🔹 اعمال فیلتر جستجو: اگر شناسه تور وجود داشت، شیء `filter` را به گونه‌ای مقداردهی می‌کنیم که دیتابیس فقط به دنبالِ نظراتی بگردد که فیلد `tour` در آن‌ها با این شناسه برابر باشد.

## فصل نهم: طراحی معماری Handler Factory (کاهش کدهای تکراری)

در این فصل، یک سیستم `Handler Factory` قدرتمند برای استانداردسازی عملیات‌های پایگاه داده ایجاد می‌کنیم. در کنترلرهای مختلف (مثل تورها، کاربران و نظرات)، توابع حذف، ایجاد و به‌روزرسانی بسیار شبیه به هم هستند. اگر بخواهیم یک تغییر کوچک (مثلاً تغییر پیام سیستم یا `HTTP Status Code`) ایجاد کنیم، باید تمام هندلرها را به صورت دستی ویرایش کنیم که باعث تولید حجم زیادی از کدهای تکراری (`Duplicate Code`) می‌شود.

راه‌حل این مشکل، استفاده از توابع کارخانه (`Factory Functions`) است؛ توابعی که وظیفه‌شان تولید و بازگرداندن توابع هندلر است.

> 💡 **نکته طلایی معماری:** یک فکتوری فانکشن (`Factory Function`) تابعی است که یک تابع دیگر (در اینجا یک هندلر `async`) را برمی‌گرداند. این الگو به لطف ویژگی کلوژرها (`Closures`) در جاوااسکریپت کار می‌کند؛ زیرا تابع داخلیِ تولید شده، حتی پس از اجرای تابع خارجی، به متغیرهای آن (مثل متغیر `Model`) دسترسی کامل دارد.

### ۱. توابع عملیاتی پایه (Delete, Update, Create)

برای استانداردسازی این عملیات‌ها، توابع زیر در فکتوری ساخته شدند:

- 🔹 **عملیات حذف (`deleteOne`):** این تابع مدل دیتابیس (`Model`) را به عنوان ورودی می‌گیرد و کدهای مربوط به `findByIdAndDelete` را برای آن مدل خاص تولید می‌کند.

- 🔹 **عملیات به‌روزرسانی (`updateOne`):** این تابع دقیقاً مشابه حذف است، با این تفاوت که از متد `findByIdAndUpdate` استفاده می‌کند و داده‌های جدید را از `req.body` می‌گیرد.

- 🔹 **عملیات ایجاد (`createOne`):** این تابع با استفاده از متد `create` یک داکیومنت جدید می‌سازد.

**حل یک چالش در مسیرهای تودرتو (`Nested Routes`):**
در کنترلر نظرات، عملیات ساخت یک نظرِ جدید نیازمند تنظیم دستیِ شناسه تور (`tourId`) و شناسه کاربر (`userId`) بود. برای اینکه بتوانیم از فکتوریِ عمومیِ `createOne` استفاده کنیم، این منطق را از کنترلرِ ساخت جدا کرده و در یک میدل‌ورِ اختصاصی به نام `setTourUserIds` قرار دادیم. با این کار، کنترلر نظرات کاملاً ایزوله و مستقل شد.

### ۲. توابع خواندن اطلاعات (Read Operations)

نوشتن فکتوری برای واکشی داده‌ها کمی پیچیده‌تر است، زیرا با چالش‌هایی مثل مقادیر `Populate` و فیلترهای جستجو مواجه هستیم:

- 🔹 **عملیات دریافت یک آیتم (`getOne`):** چالش این بخش، پشتیبانی از متد `populate` بود که در کنترلر تورها به آن نیاز داشتیم. برای حل این مشکل، فکتوری `getOne` علاوه بر متغیر `Model`، یک پارامتر اختیاری به نام `popOptions` دریافت می‌کند. سیستم ابتدا کوئری را می‌سازد؛ اگر آپشنی برای واکشی وجود داشت آن را به کوئری متصل (`Chain`) می‌کند و در نهایت کوئریِ نهایی را `await` می‌کند.

- 🔹 **عملیات دریافت همه آیتم‌ها (`getAll`):** در این تابع، کلاس `APIFeatures` را به صورت کامل ادغام کردیم تا تمام موجودیت‌ها به قابلیت‌های فیلتر، مرتب‌سازی و صفحه‌بندی دسترسی داشته باشند. همچنین برای پشتیبانی از مسیرهای تودرتوی نظرات (`Nested GET Reviews`)، یک متغیر فیلترِ کوچک به صورت هک (`Hack`) اضافه کردیم تا در صورت وجود `tourId` در مسیر، فقط نظراتِ همان تور واکشی شوند.

### 🗺️ دیاگرام جریان فکتوری و میدل‌ور

```text
       ▼
[ Router ] ──> [ setTourUserIds ] (اضافه کردن خودکار ID به بادی)
                       │
                       ▼
               [ factory.createOne(Review) ] (استفاده از هندلر عمومی)
                       │
                       ▼
                  [ Database ]

```

### 💻 پیاده‌سازی نهایی در کنترلر نظرات

با استفاده از معماری جدید، فایل کنترلرِ نظراتِ ما (`reviewController.js`) فوق‌العاده تمیز، کوتاه و خوانا شد:

```javascript
const Review = require('../models/reviewModel');
const factory = require('./handlerFactory');

// میدل‌ور برای پشتیبانی از مسیرهای تودرتو
exports.setTourUserIds = (req, res, next) => {
  if (!req.body.tour) req.body.tour = req.params.tourId;
  if (!req.body.user) req.body.user = req.user.id;
  next();
};

// تولید هندلرها تنها در 1 خط کد
exports.getAllReviews = factory.getAll(Review);
exports.getReview = factory.getOne(Review);
exports.createNewReview = factory.createOne(Review);
exports.updateReview = factory.updateOne(Review);
exports.deleteReview = factory.deleteOne(Review);
```

> 🎯 **نتیجه‌گیری استراتژیک:** با این 5 تابعِ فکتوری، ما یک معماریِ بسیار منعطف ساختیم. اکنون اگر بخواهیم یک منبع جدید (مانند سیستم رزروها یا `Bookings`) به پروژه اضافه کنیم، می‌توانیم کل هسته‌ی API آن را در عرض 5 ثانیه و بدون نوشتن حتی یک خط منطقِ تکراری راه‌اندازی کنیم.
